Gateway 8: Documentation & Examples --- Verification Guide
===========================================================

This document maps each Gateway 8 deliverable to its implementation,
tests, and evidence.  A judge can verify compliance by reading this
document top-to-bottom and running the commands in each section.

**Success metric (competition README):** complete API docs + examples.

Quick Build & Run
-----------------

.. code-block:: bash

   task docs-build            # Execute notebooks + build the Sphinx site
   task docs-serve            # Serve it locally
   uv run python examples/01_transmit.py    # 12-s I/Q signal file
   uv run python examples/02_decode.py      # decode a signal file
   uv run python examples/03_round_trip.py  # transmit → decode, bit-exact

``.github/workflows/docs-pages.yml`` deploys the site to GitHub Pages on
every push to ``main`` once the repository is public; until then
``task docs-serve`` renders the same build locally.
``task docs-build`` runs with Sphinx ``-W`` (warnings are errors), so a
broken cross-reference or an orphaned page fails the build; the same build
runs as a required check in ``docs-check.yml``.

GD8.1 --- API reference
-----------------------

:doc:`api` is generated by Sphinx ``autodoc`` directly from the shipped
docstrings, so it cannot drift from the code.  ``scripts/sync_docstrings.py``
also asserts that the C++ header ``@param`` tags and the Python
binding docstrings stay in sync; it runs inside ``task lint-check``, which is
a required check in ``lint.yml`` and part of ``task ci-checks``.

The API is documented in three layers, matching the three layers a caller
can enter at (see :doc:`quickstart` §*API Layers*):

.. list-table::
   :widths: 20 40 40
   :header-rows: 1

   * - Layer
     - Surface
     - Reference
   * - Layer 2 (high level)
     - ``receive_frame()``, ``transmit_frame()``, result dataclasses
     - :doc:`api` §*High-Level API*
   * - Layer 1 (wrappers)
     - ``frame_build()``, ``frame_decode()``, ``parse_sb2()``, …
     - :doc:`api` §*Low-Level API*
   * - Layer 0 (C++)
     - ``lunalink_core`` public headers, nanobind extension
     - :doc:`api_cpp` --- every public entity rendered from the headers by
       Doxygen and Breathe; :doc:`signal/icd` --- the Interface Control
       Document with error codes and thread-safety per function

.. code-block:: bash

   task sync-docstrings   # asserts docstrings match binding signatures
   task docs-build        # -W: any autodoc failure is a build failure

GD8.2 --- Worked examples
-------------------------

Three runnable scripts cover the full chain end to end.  Each runs from a
clean checkout after ``task install`` with no arguments and no setup.

.. list-table::
   :widths: 30 70
   :header-rows: 1

   * - Script
     - What it demonstrates
   * - ``examples/01_transmit.py``
     - Build a 12-second navigation frame and modulate it to a baseband
       I/Q file with the ``LSISIQ`` metadata header (~491 MB at the
       native 5.115 MHz chip rate)
   * - ``examples/02_decode.py``
     - Read an I/Q file back, synchronise, and decode to parsed
       navigation data
   * - ``examples/03_round_trip.py``
     - Transmit → decode → assert bit-exact recovery of every subframe
   * - ``demo/v1_plot.py``
     - Signal-chain visualisation (writes ``demo/v1_signal.png``)

.. code-block:: bash

   uv run python examples/03_round_trip.py
   # transmit → decode → bit-exact comparison, exit code 0

Real-time margin
~~~~~~~~~~~~~~~~

The chain processes a 12-second frame faster than the frame's own
duration, which is the condition for real-time operation:

.. list-table::
   :widths: 40 30 30
   :header-rows: 1

   * - Metric
     - Requirement
     - Measured
   * - Real-time capable
     - Faster than signal duration
     - 12 s signal processed in < 1 s
   * - LDPC convergence
     - Within the 50-iteration cap
     - Knee at ~15 iterations

Timing determinism is gated, not merely benchmarked — and scoped
honestly.  ``task constant-time`` times the input-independent primitives
(BPSK modulator, CRC-24, interleaver, exhaustive-ML BCH decoder) across
adversarial input classes (all-zeros, all-ones, pseudo-random) and fails if
the class-to-class spread exceeds 14%, a ceiling set at twice the worst
value measured over eight idle runs; that is what makes the branchless
mandate a measured property rather than a design intent.  The LDPC and
frame decoders are excluded by design: they early-terminate on a satisfied
syndrome, so their worst case is bounded by the forced full-iteration
budgets that ``task wcet`` asserts instead.  See
:doc:`assurance/mission_assurance` §*Time-Deterministic Execution*.

.. _channel performance:

Channel performance
~~~~~~~~~~~~~~~~~~~

Full characterisation, including 95% Wilson confidence intervals and the
Shannon-gap decomposition, is in :doc:`signal/ldpc_performance` and
:doc:`signal/bch_performance`.  Headline results:

.. list-table::
   :widths: 34 66
   :header-rows: 1

   * - Result
     - Value
   * - LDPC SF2 BER at Eb/N0 = 3.0 dB
     - 0 bit errors in 18,000,000 bits
   * - LDPC SF3/SF4 BER at Eb/N0 = 3.0 dB
     - 0 bit errors in 13,050,000 bits
   * - Error-floor search
     - 0 errors in 60,000 frames per point; no floor observable to
       6.4 × 10\ :sup:`-5`
   * - Gap to reference belief propagation
     - Within 0.15 dB (the ~1.0 dB total gap is the n=2400 code's, not
       the implementation's)
   * - BCH soft- vs hard-decision gain
     - ~2 dB of link budget
   * - Input-LLR quantisation
     - int8 costs no measurable performance --- an 8-bit ADC front-end
       suffices

.. note::

   The spec phrase "SNR > 0 dB" is ambiguous.  Both interpretations are
   reported, and the requirement is met under each; see
   :doc:`signal/ldpc_performance` §*SNR Interpretation Note*.

.. code-block:: bash

   task performance   # WCET timing + BER/FER waterfalls (longer run)
   task ber           # BER/FER sweeps only

----------------------------------

Each significant algorithm choice is recorded with its rationale, its
alignment to the spec's equations, and its trade-offs --- not only what was
implemented but why:

.. list-table::
   :widths: 34 66
   :header-rows: 1

   * - Document
     - Records
   * - :doc:`signal/algorithms`
     - Numerical policy: IEEE-754 float64, ``-fno-fast-math``, fixed
       layered update order giving bit-reproducible results across
       conforming toolchains
   * - :doc:`signal/bch_decoder_design`
     - Why exhaustive-ML over an algebraic t=2 decoder, and why both a
       hard- and a soft-decision variant ship
   * - :doc:`signal/ldpc_algo_card`
     - Layered sum-product schedule, the clamped φ-transform with its
       worst-case error analysis, and the reference-decoder comparison
   * - :doc:`gateway0`
     - Milestone-1 architecture decisions: no exceptions, no RTTI, no
       heap on the signal path
   * - :doc:`signal/spec_findings_report`
     - Ambiguities found in LSIS V1.0 and the resolutions adopted
